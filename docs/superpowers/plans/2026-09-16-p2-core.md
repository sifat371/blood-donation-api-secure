# P2 Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace startup schema mutation with data-preserving Alembic migrations and replace single-donor blood-request acceptance with a race-safe multi-donor commitment model where one donor represents one unit and committed/completed units are tracked separately.

**Architecture:** Alembic becomes the canonical schema owner for SQLite and PostgreSQL. `BloodRequest` remains the parent aggregate while a new `DonationCommitment` table owns donor participation; all REST and MCP lifecycle operations delegate to one transactional service layer that derives request status from commitments. Existing P1 SQLite databases are verified, backed up, stamped at a P1 baseline revision, and upgraded in place.

**Tech Stack:** Python 3.11+, FastAPI, SQLModel/SQLAlchemy 2, Alembic 1.x, SQLite, PostgreSQL 16+, psycopg 3, Pydantic v2, pytest, GitHub Actions, uv.

**Spec:** `docs/superpowers/specs/2026-09-16-p2-core-design.md`

## Global Constraints

- Preserve existing P1 SQLite data; no destructive reset.
- One donor represents exactly one unit per blood request.
- Track committed units separately from completed units.
- Request lifecycle: `Pending`, `Partially Committed`, `Fully Committed`, `Completed`, `Cancelled`, `Expired`.
- Existing `Accepted` status is migration input only and must not be produced by P2 runtime behavior.
- Do not fabricate missing historical donors/units.
- P0 privacy/authentication guarantees and P1 transaction guarantees must remain intact.
- `blood_requests.accepted_by` is migration input only and is removed after data transformation.
- Application startup must not mutate schemas.
- PostgreSQL 16 or newer is the CI production target; SQLite remains supported for development/tests and existing installs.
- Push delivery remains best-effort and happens only after the database transaction commits.
- Human confirmation UX for AI mutations, durable notification outbox, moderation, and frontend redesign are out of P2 scope.

```python
    config.set_main_option("sqlalchemy.url", settings.database_url)
target_metadata = SQLModel.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=config.get_main_option("sqlalchemy.url"),
        target_metadata=target_metadata,
        literal_binds=True,
        compare_type=True,
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata, compare_type=True)
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

```python
from alembic.config import Config
from alembic.script import ScriptDirectory
from sqlalchemy import inspect, text


def expected_head() -> str:
    return ScriptDirectory.from_config(Config("alembic.ini")).get_current_head()


def assert_schema_at_head(engine) -> None:
    if "alembic_version" not in inspect(engine).get_table_names():
        raise RuntimeError("Database is not Alembic-versioned; run the migration/bootstrap command before starting the API")
    with engine.connect() as conn:
        current = conn.execute(text("SELECT version_num FROM alembic_version")).scalar_one_or_none()
    head = expected_head()
    if current != head:
        raise RuntimeError(f"Database schema revision {current!r} is behind expected Alembic head {head!r}; run 'uv run alembic upgrade head'")
```
